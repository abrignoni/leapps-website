# Telegram System Events: The Cross-Platform Reference

This is the companion to [Telegram on Both Sides](https://www.leapps.org/blog-post?post=2026-08-04-telegram-ios-android-coverage), which covers what iLEAPP and ALEAPP now parse out of Telegram. This one answers the narrower question that comes up in casework: what system events can Telegram even record, and what do they mean?

[Download the printable PDF edition](https://leapps-api.4n6-198.workers.dev/downloads/telegram-system-events-reference.pdf).

Telegram does not only store what people typed. It stores events. Somebody was added to a group. A screenshot was taken. The history was cleared. The auto-delete timer moved from off to twenty four hours. A call happened, and it was missed rather than answered. Those live in the message table alongside the chat text, and they are frequently the records that answer the question you actually have.

## Why this document exists

The two clients name the same event differently.

That sounds like trivia until you are reading an iLEAPP report and an ALEAPP report side by side. A user being added to a group is `addedMembers` on iOS and `ChatAddUser` on Android. A screenshot in a secret chat is `historyScreenshot` on one and `ScreenshotTaken` on the other. Content protection is `copyProtectionToggle` here and `NoForwardsToggle` there.

I checked how bad it is. Of roughly seventy distinct events, **matching the two lists by name alone pairs only 27 of them.** The rest are the same concept wearing different clothes. So if you work both platforms, and most of us do, you need a translation table, and as far as I can tell nobody had published one.

## How this was built, and how far to trust it

The two per-platform lists are extracted from the clients' own published source, not retyped: the iOS ordinals come from `SyncCore_TelegramMediaAction.swift`, and the Android constructors come from the generated `TlGen_MessageAction.kt`. A script in the site repository does the extraction so this page can be refreshed rather than rewritten. That matters more than it sounds: iLEAPP's own copy of the iOS list had drifted twenty entries out of date before this work, and Telegram keeps adding events.

**Every event name in the tables is a link to the line of Telegram's source that defines it.** Do not take my word for any row. Click the name and read the client's own code.

Those links are pinned to a specific commit rather than to `main`, on purpose. Line numbers move with every upstream edit, so a link to `main` would keep working while quietly pointing at the wrong line, which is worse than a broken link. The iOS side is pinned at `3344a18d3cdc` and the Android side at `9bcf3d2769c6`. When this reference is refreshed, the script re-pins both and every line number is re-derived.

The cross-platform pairing is the part a machine cannot do. String matching gets you 27. The remaining pairs were mapped by hand and reviewed. Where I could not find a counterpart, the row says so with a dash rather than guessing.

As of the source on August 4, 2026: **iOS defines 64 event types** with ordinals up to 65, and **Android defines 68**, spread across 107 constructors because Android versions each event per protocol layer. 62 pair across platforms.

Three things to keep in mind before any of this goes in a report:

- **A name is not proof.** These tables tell you what the record type means. Whether the event happened as alleged still depends on the record, the timestamps around it, and your validation.
- **Payload decoded** in the last column means our parsers pull the detail fields out, not merely name the event. A phone call reports its outcome and duration; a timer change reports the new value. Where the column is blank the event is named but its payload is not broken out.
- **These lists drift.** Refresh from source before relying on the absence of something.

## Reading the asymmetries

A few of the gaps above are worth a sentence, because they are the sort of thing that looks like a parser bug when it is actually the platform.

**Android has `ChannelCreate` and iOS does not.** iOS folds channel creation into the migration and group creation events rather than emitting a distinct one.

**Android has bot-side twins**, `PaymentSentMe` and `WebViewDataSentMe`, which record the same transaction from the receiving bot's perspective. You will not see these on a normal user's device.

**`Empty` exists on Android** as a placeholder with no content. If you see it, it is not a parsing failure.

**iOS `botDomainAccessGranted` and `botAppAccessGranted` both map to Android `BotAllowed`.** iOS splits website login from mini app authorization; Android does not.

## What the parsers do with these

On both platforms every event in these tables is named in the report rather than shown as an unlabelled system message. That was not true before this summer: iOS was reporting twenty of them as "unknown" because its list had gone stale, and Android was collapsing all of them into one flat label.

The events whose payloads we break out are marked in the last column. The one I would point at first is the phone call, because on Android it turns what used to be an unreadable row into a call log entry with an outcome and a duration.
